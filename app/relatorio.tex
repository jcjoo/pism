\begin{resumo}
O presente trabalho descreve o desenvolvimento do SalesPro, um aplicativo mobile criado para auxiliar trabalhadores autônomos que realizam vendas porta a porta. O sistema oferece funcionalidades de cadastro e gerenciamento de clientes e produtos, registro de vendas com suporte a pagamentos à vista e parcelados, controle de recebimentos com visualização em calendário e otimização de rotas de cobrança com base na posição GPS atual do vendedor. A otimização de rotas é realizada em três etapas: priorização por urgência de vencimento, seleção por capacidade de horas disponíveis e reordenação geográfica pelo algoritmo do vizinho mais próximo partindo da localização atual do dispositivo, com distâncias calculadas pela fórmula de Haversine. Para garantir o funcionamento sem conectividade, os dados são sincronizados localmente via AsyncStorage com fila de operações pendentes. A solução foi construída com React Native e Expo no front-end, utilizando NativeWind para estilização e Supabase como plataforma de back-end, com banco de dados PostgreSQL, autenticação integrada e políticas de segurança em nível de linha (RLS).

 \textbf{Palavras-chaves}: aplicativo mobile. React Native. Expo. Supabase. gestão de vendas. otimização de rotas. modo offline.
\end{resumo}

% resumo em inglês
\begin{resumo}[Abstract]
 \begin{otherlanguage*}{english}
   This work describes the development of SalesPro, a mobile application designed to assist autonomous workers who perform door-to-door sales. The system provides features for registering and managing clients and products, recording sales with support for cash and installment payments, tracking receivables through a calendar view, and optimizing collection routes based on the vendor's current GPS position. Route optimization is performed in three steps: prioritization by payment urgency, selection based on available working hours, and geographic reordering using a nearest-neighbor heuristic starting from the device's current location, with distances calculated via the Haversine formula. Local data synchronization via AsyncStorage with an offline operation queue ensures full functionality without network connectivity. The solution was built with React Native and Expo, using NativeWind for styling and Supabase as the back-end platform, with a PostgreSQL database, integrated authentication, and row-level security (RLS) policies.

   \vspace{\onelineskip}

   \noindent
   \textbf{Key-words}: mobile application. React Native. Expo. Supabase. sales management. route optimization. offline mode.
 \end{otherlanguage*}
\end{resumo}

\chapter*[Introdução]{Introdução}

% ----------------------------------------------------------

O comércio porta a porta é uma realidade para milhares de trabalhadores autônomos no Brasil. Esses profissionais gerenciam, de forma manual ou com ferramentas genéricas como planilhas e cadernos, um volume crescente de informações: dados de clientes, catálogos de produtos, condições de pagamento e controle de recebimentos. A ausência de uma ferramenta digital especializada para esse perfil de trabalhador gera retrabalho, perda de informações e dificuldade no acompanhamento de valores em aberto.

Além do controle financeiro, a logística diária de visitas representa outro desafio: sem uma rota otimizada, o vendedor percorre distâncias desnecessárias entre os clientes, desperdiçando tempo e combustível. Agrava esse cenário o fato de que muitos vendedores atuam em regiões com conectividade móvel instável ou inexistente, tornando inviável o uso de aplicativos dependentes de conexão constante com a internet.

O SalesPro foi desenvolvido para responder a esses dois eixos de necessidade. É um aplicativo mobile que centraliza a gestão comercial do autônomo — clientes, produtos, vendas e recebimentos — e ainda calcula automaticamente a melhor sequência de cobranças do dia partindo da localização GPS atual do vendedor, funcionando de forma completa mesmo sem acesso à rede.

Este relatório descreve o processo de desenvolvimento do SalesPro, cobrindo a proposta do projeto, as decisões arquiteturais e tecnológicas, o fluxo das funcionalidades implementadas, o algoritmo de otimização de rotas, as estratégias de segurança adotadas e a preparação para distribuição do aplicativo.

\chapter{Descrição do Problema e Solução}

\section{Contexto e Problema}

Trabalhadores autônomos que atuam com vendas porta a porta enfrentam desafios cotidianos na organização de suas atividades comerciais. Entre os principais problemas identificados estão:

\begin{itemize}
  \item Dificuldade em manter um cadastro atualizado de clientes, com endereço, coordenadas geográficas e dados de contato;
  \item Ausência de controle de estoque e catálogo de produtos com preços;
  \item Falta de rastreamento de vendas realizadas e seus respectivos status de pagamento;
  \item Dificuldade em identificar parcelas em aberto e pagamentos em atraso;
  \item Ausência de visão consolidada dos valores a receber;
  \item Rotas de cobrança não otimizadas, com deslocamentos desnecessários entre clientes;
  \item Dependência de conectividade para acessar informações no campo.
\end{itemize}

Sem uma ferramenta adequada, esses trabalhadores frequentemente perdem o controle financeiro de suas operações, acumulando inadimplência não monitorada, desperdiçando tempo em processos manuais e percorrendo rotas ineficientes ao longo do dia.

\section{Solução Proposta}

O SalesPro é um aplicativo mobile que centraliza toda a gestão comercial do vendedor autônomo em uma única plataforma. A solução oferece:

\begin{itemize}
  \item \textbf{Cadastro de clientes}: registro de nome, CPF, telefone, e-mail, endereço com busca automática por CEP e coordenadas geográficas via Nominatim/OpenStreetMap;
  \item \textbf{Catálogo de produtos}: gerenciamento de produtos com nome, descrição, preço e controle de estoque;
  \item \textbf{Registro de vendas}: criação de pedidos com múltiplos itens, suporte a pagamento à vista ou parcelado (2x a 6x), com data de vencimento configurável;
  \item \textbf{Controle de recebimentos}: calendário interativo que exibe os pagamentos pendentes por data, classificados por status (atrasado, vence hoje, a vencer), com modo manual e modo de rota;
  \item \textbf{Dashboard}: painel inicial com resumo do total a receber, calendário mensal de vencimentos e alertas de parcelas em atraso;
  \item \textbf{Otimização de rotas de cobrança}: cálculo automático da sequência ideal de visitas com base na localização GPS atual do vendedor e nas coordenadas dos clientes, usando heurística do vizinho mais próximo; interface de swipe para registrar recebimentos em campo;
  \item \textbf{Gestão de regiões}: controle das cidades atendidas pelo vendedor, vinculadas aos cadastros de clientes;
  \item \textbf{Relatórios}: visão analítica das operações — produtos mais vendidos, clientes que mais compram, faturamento mensal e vendas em aberto;
  \item \textbf{Funcionamento offline}: cache local via AsyncStorage com fila de sincronização para operações realizadas sem conexão.
\end{itemize}

\chapter{Stack Tecnológico}

\section{Front-End}

O front-end do SalesPro foi desenvolvido com \textbf{React Native} via \textbf{Expo SDK 55}, framework que permite criar aplicativos para Android e iOS a partir de uma única base de código em TypeScript. A escolha pelo Expo se justifica pela abstração do processo de build e pelo conjunto de APIs nativas já integradas, como localização geográfica (\texttt{expo-location}) e seletor de datas.

Para a estilização, foi adotado o \textbf{NativeWind v4}, que traz a sintaxe utilitária do Tailwind CSS para o React Native, permitindo que os estilos sejam definidos diretamente nas classes dos componentes e eliminando grande parte do código de \textit{StyleSheet} convencional. Classes utilitárias customizadas são definidas em \texttt{global.css} e configuradas em \texttt{tailwind.config.js}.

A linguagem principal é \textbf{TypeScript}, que adiciona tipagem estática ao JavaScript, aumentando a segurança do código, facilitando a detecção precoce de erros e melhorando a produtividade no desenvolvimento. Os tipos do banco de dados são gerados automaticamente pelo Supabase CLI em \texttt{src/types/database.types.ts}.

\section{Navegação}

A navegação entre telas é gerenciada pelo \textbf{React Navigation}, com dois navegadores principais:

\begin{itemize}
  \item \texttt{createNativeStackNavigator}: pilha principal que separa a tela de autenticação do restante do app;
  \item \texttt{createBottomTabNavigator}: barra de abas inferior com Início, Nova Venda, Vendas e Rota (Recebimentos). Telas secundárias (Clientes, Produtos, Regiões, Conta, Relatórios) são acessadas via menu lateral hambúrguer.
\end{itemize}

A tela de Menu é apresentada como modal com transição lateral, preservando o contexto da tela anterior. Um header customizado (\texttt{header.tsx}) compartilhado por todas as telas exibe o título e o botão hambúrguer de acesso ao menu.

\section{Back-End e Banco de Dados}

O back-end é fornecido pelo \textbf{Supabase}, plataforma BaaS de código aberto construída sobre PostgreSQL. O Supabase oferece:

\begin{itemize}
  \item \textbf{Banco de dados PostgreSQL}: banco relacional com suporte a relacionamentos e políticas de segurança;
  \item \textbf{Autenticação integrada}: gerenciamento de sessões com JWT, com \textit{refresh tokens} automáticos e persistência via \texttt{AsyncStorage};
  \item \textbf{API REST auto-gerada}: cada tabela expõe endpoints REST protegidos automaticamente via PostgREST;
  \item \textbf{Row Level Security (RLS)}: políticas que garantem que cada usuário acesse apenas seus próprios registros.
\end{itemize}

A comunicação é feita pelo cliente oficial \texttt{@supabase/supabase-js}, com credenciais fornecidas via variáveis de ambiente (\texttt{EXPO\_PUBLIC\_SUPABASE\_URL} e \texttt{EXPO\_PUBLIC\_SUPABASE\_ANON\_KEY}).

\section{Geocodificação}

A geolocalização de endereços de clientes é feita via \textbf{Nominatim (OpenStreetMap)}, serviço gratuito e sem necessidade de chave de API. O \texttt{geocoding.service.ts} implementa três operações: busca precisa por endereço completo, busca pelo centro da cidade como fallback, e geração de sugestões de autocompletar com debounce de 500ms para o campo de endereço. As coordenadas obtidas (\texttt{latitude}/\texttt{longitude}) são persistidas no cadastro do cliente e usadas pelo algoritmo de otimização de rotas.

O acesso à posição GPS do dispositivo é feito via \textbf{expo-location}, que abstrai as permissões e APIs de localização de cada plataforma. A posição atual é solicitada no momento da geração da rota para usar como ponto de partida do algoritmo.

\section{Armazenamento Local e Sincronização Offline}

O \textbf{AsyncStorage} (\texttt{@react-native-async-storage/async-storage}) é utilizado como camada de persistência local, com duas finalidades distintas:

\begin{itemize}
  \item \textbf{Cache de listas}: clientes, produtos e vendas pendentes são armazenados localmente após cada busca bem-sucedida ao Supabase, e carregados diretamente do cache quando offline;
  \item \textbf{Fila de sincronização}: operações de recebimento realizadas offline (como marcar uma parcela como recebida) são enfileiradas localmente e enviadas ao Supabase quando a conexão é restabelecida pelo \texttt{sync.service.ts}.
\end{itemize}

O estado global de sincronização é gerenciado pelo \texttt{SyncContext}, que expõe o status (\textit{idle / syncing / synced / error}), a contagem de operações pendentes e um toggle de auto-sincronização a cada 3 minutos.

\section{Testes}

A suíte de testes é composta por \textbf{Jest} com \textbf{React Testing Library for React Native}, cobrindo testes unitários dos componentes principais (Button, QuantitySelector) e testes dos serviços de negócio (\texttt{sales.service}), com mocks do cliente Supabase.

\section{Visão em Camadas}

O projeto segue uma arquitetura em camadas que separa responsabilidades de forma clara:

\begin{itemize}
  \item \textbf{Screens (Telas)}: componentes React Native responsáveis pela interface e interação com o usuário. Cada tela concentra a lógica de apresentação e delega operações de dados à camada de serviços;
  \item \textbf{Services (Serviços)}: módulos que encapsulam toda a comunicação com o Supabase e com o armazenamento local. Cada entidade do domínio possui seu próprio serviço: \texttt{clients.service.ts}, \texttt{products.service.ts}, \texttt{sales.service.ts}, \texttt{recebimentos.service.ts}, \texttt{relatorios.service.ts} e \texttt{endereco.service.ts};
  \item \textbf{Context}: estado global de sincronização offline exposto via \texttt{SyncContext}, consumido pelo menu e pelas telas de recebimento;
  \item \textbf{Hooks}: lógica de estado reutilizável extraída em hooks customizados. O principal é o \texttt{useAuth}, que expõe o estado de sessão do usuário para toda a aplicação;
  \item \textbf{Components}: biblioteca interna de componentes reutilizáveis de UI — Button, Input, Select, QuantitySelector, ConfirmDialog, Toast, Accordion, DateTime, FormScrollView;
  \item \textbf{Navigation}: camada de roteamento que controla o fluxo entre telas autenticadas e não autenticadas.
\end{itemize}

\chapter{Otimização de Rotas e Funcionamento Offline}

\section{Motivação}

A rotina do vendedor autônomo envolve visitar múltiplos clientes para cobrar pagamentos ao longo do dia. Sem uma sequência planejada, é comum percorrer distâncias desnecessárias — visitando um cliente no extremo norte do bairro, depois outro no sul, e voltando ao norte em seguida. Esse comportamento desperdiça tempo e combustível, dois recursos críticos para trabalhadores que operam com margens apertadas.

Um segundo fator agrava o problema: parte significativa das rotas de vendas ocorre em áreas periféricas ou rurais, onde a cobertura de dados móveis é instável. Soluções que dependem de chamadas constantes a serviços de roteamento na nuvem (como Google Maps Directions API) se tornam inoperantes exatamente quando mais são necessárias.

O SalesPro resolve ambos os problemas com um módulo de otimização de rotas que opera inteiramente no dispositivo, sem necessidade de rede, e calcula em milissegundos a melhor sequência de cobranças para o dia partindo da localização real do vendedor.

\section{Armazenamento Local e Sincronização Offline}

A estratégia de funcionamento offline é construída sobre o \textbf{AsyncStorage}. O fluxo de sincronização opera da seguinte forma:

\begin{enumerate}
  \item \textbf{Quando online}: ao carregar as telas de recebimentos e clientes, o app busca do Supabase os dados atualizados e os persiste localmente em AsyncStorage sob chaves identificadas pelo \texttt{user\_id};
  \item \textbf{Quando offline}: o app carrega os dados diretamente do cache local. Operações de recebimento são enfileiradas no \texttt{SYNC\_QUEUE} pelo \texttt{storage.service.ts};
  \item \textbf{Ao reconectar}: o \texttt{sync.service.ts} drena a fila (\texttt{flushQueue}), enviando as operações pendentes ao Supabase em ordem, e em seguida atualiza os caches com os dados mais recentes.
\end{enumerate}

O estado global de sincronização é exibido no menu lateral, permitindo que o vendedor acompanhe em tempo real quantas operações estão aguardando envio e quando foi a última sincronização bem-sucedida.

\section{Algoritmo de Otimização}

\subsection{Formulação do Problema}

O problema de sequenciamento de cobranças é uma instância do \textit{Traveling Salesman Problem} (TSP): dado um conjunto de $n$ pontos geográficos (clientes) e um ponto de partida (posição atual do vendedor), encontrar a ordem de visita que minimize a distância total percorrida. O TSP é NP-difícil em sua formulação exata, mas para os tamanhos práticos de instância do SalesPro — tipicamente entre 5 e 50 clientes por rota diária — a heurística do vizinho mais próximo produz soluções de boa qualidade com custo computacional desprezível.

\subsection{Cálculo de Distância — Fórmula de Haversine}

A distância entre dois pontos geográficos é calculada pela \textbf{fórmula de Haversine}, que computa a distância de grande círculo (linha reta sobre a superfície esférica da Terra) entre dois pares de coordenadas $(\varphi_1, \lambda_1)$ e $(\varphi_2, \lambda_2)$:

\begin{equation}
d = 2r \cdot \arcsin\!\left(\sqrt{\sin^2\!\left(\frac{\Delta\varphi}{2}\right) + \cos\varphi_1 \cdot \cos\varphi_2 \cdot \sin^2\!\left(\frac{\Delta\lambda}{2}\right)}\right)
\label{eq:haversine}
\end{equation}

onde $\Delta\varphi = \varphi_2 - \varphi_1$, $\Delta\lambda = \lambda_2 - \lambda_1$ e $r = 6371\,\text{km}$ é o raio médio da Terra.

\subsection{Heurística do Vizinho Mais Próximo}
\label{subsec:nn}

A construção da rota segue o algoritmo de \textit{nearest neighbor} (vizinho mais próximo):

\begin{enumerate}
  \item Obter a posição atual do vendedor via GPS (\texttt{expo-location}), solicitando a permissão em tempo de execução;
  \item Inicializar a rota encontrando o cliente mais próximo da posição atual do dispositivo;
  \item Para cada passo seguinte, calcular a distância Haversine entre o último cliente visitado e todos os clientes ainda não selecionados;
  \item Selecionar o cliente com menor distância e adicioná-lo à rota;
  \item Repetir os passos 3 e 4 até que todas as paradas selecionadas estejam na rota.
\end{enumerate}

A complexidade do algoritmo é $O(n^2)$ em relação ao número de clientes $n$, o que para $n = 50$ resulta em 2.500 operações — executadas em tempo imperceptível em qualquer dispositivo mobile moderno.

Caso a permissão de localização seja negada pelo usuário, o algoritmo inicia pelo cliente de maior urgência de vencimento como fallback, preservando o funcionamento da funcionalidade.

\section{Otimização de Sequência nos Recebimentos}

O módulo de Rota de Recebimento combina priorização por urgência financeira com reordenação geográfica, operando inteiramente no dispositivo sem acesso à rede.

\subsection{Etapas do Algoritmo}

A construção da rota de recebimentos segue três etapas sequenciais:

\begin{enumerate}
  \item \textbf{Pontuação por urgência}: cada recebimento pendente recebe uma pontuação baseada no status do vencimento da parcela mais próxima — atrasado ($-1000 + \Delta d$), vence hoje ($0$), esta semana ($\Delta d$) ou futuro ($100 + \Delta d$), onde $\Delta d$ é o número de dias até o vencimento. A pontuação mais baixa indica maior urgência;

  \item \textbf{Seleção por capacidade}: o conjunto de paradas é ordenado por urgência e truncado ao máximo de paradas que cabem no dia, calculado como:
  \begin{equation}
    n_{\max} = \left\lfloor \frac{H_{\text{disp}} \times 60}{\bar{t}_{\text{parada}}} \right\rfloor
    \label{eq:maxstops}
  \end{equation}
  onde $H_{\text{disp}}$ é o número de horas disponíveis e $\bar{t}_{\text{parada}}$ é o tempo médio estimado por parada (ambos configuráveis pelo usuário);

  \item \textbf{Reordenação geográfica}: as paradas selecionadas são reordenadas pelo algoritmo do vizinho mais próximo (Seção~\ref{subsec:nn}), partindo da localização GPS atual do vendedor — garantindo que a primeira visita do dia seja o cliente mais próximo da posição de saída — e construindo o restante da rota de forma gulosa para minimizar o deslocamento total.
\end{enumerate}

\subsection{Tratamento de Coordenadas Ausentes}

Quando um cliente não possui coordenadas cadastradas (campos \texttt{latitude} e \texttt{longitude} nulos), a etapa de reordenação geográfica é ignorada para aquela parada: o algoritmo mantém a posição imediatamente após o último ponto com coordenada válida, preservando a sequência por urgência como fallback. Isso garante que a funcionalidade opere corretamente mesmo em cadastros incompletos, sem exigir conectividade para consultar APIs de geocodificação externas.

\chapter{Interface e Experiência do Usuário}

\section{Identidade Visual}

O SalesPro adota uma paleta centrada em tons de roxo — \texttt{\#3C096C} como cor primária escura, \texttt{\#5A189A} como primária e \texttt{\#E1DAE8} como fundo suave — transmitindo seriedade e confiança. Os indicadores de status de pagamento seguem codificação semântica: vermelho (\texttt{\#DF1515}) para atrasos, laranja (\texttt{\#FF8C00}) para vencimentos do dia e roxo para vencimentos futuros. O mesmo sistema de cores é reutilizado nos pontos do calendário e nos badges de status em toda a aplicação, mantendo consistência visual entre os módulos.

\section{Navegação e Usabilidade}

A navegação principal segue o padrão de \textit{bottom tab bar}, consolidado em aplicativos mobile. As quatro abas principais — Início, Nova Venda, Vendas e Rota — cobrem o fluxo diário do vendedor. As telas de gerenciamento (Clientes, Produtos, Regiões, Conta, Relatórios) são acessadas por um menu lateral hambúrguer, evitando poluição visual na barra de abas.

A interface prioriza ações rápidas: o vendedor registra uma venda completa em menos de um minuto, com seletores modais para cliente e produto, carrinho com edição inline e confirmação em um único botão. A interface de swipe na rota de recebimentos foi projetada para uso em campo com uma mão, com alvos de toque amplos e feedback visual imediato.

\section{Componentes Reutilizáveis}

A aplicação conta com uma biblioteca interna de componentes padronizados:

\end{itemize}

\chapter{Integração com API e Segurança}

\section{Comunicação com o Supabase}

Toda a comunicação com o back-end é feita via \texttt{@supabase/supabase-js}, que abstrai as chamadas HTTP à API REST gerada pelo PostgREST. Seleções com \textit{joins}, filtros encadeados, ordenação e operações de escrita são expressos de forma declarativa no TypeScript, sem SQL manual.

Operações compostas são tratadas sequencialmente com verificação de erro em cada etapa. O exemplo mais representativo é o registro de uma venda parcelada, que executa três inserções em sequência: venda, itens e parcelas. Se qualquer etapa falhar, o erro é propagado ao componente e exibido via Toast, sem estado parcial silencioso.

\section{Endpoints Protegidos e Row Level Security}

O Supabase utiliza JWT para autenticar as requisições. O \textit{anon key} embutido no app é uma chave pública que permite apenas as operações explicitamente liberadas por políticas RLS — sem a sessão de um usuário autenticado, nenhum dado de clientes, vendas ou produtos pode ser lido ou escrito.

Cada política RLS verifica se o campo \texttt{user\_id} do registro corresponde à função \texttt{auth.uid()} da sessão ativa:

\begin{verbatim}
-- Exemplo de política RLS na tabela clients
CREATE POLICY "user_can_see_own_clients"
ON clients FOR SELECT
USING (user_id = auth.uid());
\end{verbatim}

Essa abordagem garante o isolamento total entre os dados de usuários distintos diretamente no banco, sem depender de lógica de filtragem na aplicação.

\section{Variáveis de Ambiente}

As credenciais de acesso ao Supabase são carregadas de variáveis de ambiente com prefixo \texttt{EXPO\_PUBLIC\_}, que o Expo injeta no bundle durante a compilação. O arquivo \texttt{.env} não é versionado no repositório, evitando exposição acidental de chaves em histórico de commits.

\section{Estratégia de Testes}

Os testes automatizados cobrem dois níveis:

\begin{itemize}
  \item \textbf{Testes de componentes}: renderização e comportamento interativo de Button e QuantitySelector, verificando respostas a eventos de pressão, estados disabled e mudanças de valor com limites mínimos;
  \item \textbf{Testes de serviços}: lógica do \texttt{salesService} com o cliente Supabase substituído por mock. Os casos testados incluem criação de vendas à vista, geração correta de registros de parcelas para vendas parceladas e propagação de erros retornados pelo banco.
\end{itemize}

Os testes são executados com Jest e \texttt{jest-expo}, configurado para simular o ambiente React Native. O comando de execução é \texttt{npm test}.

\section{Erros Identificados Durante os Testes}

Durante os testes manuais do aplicativo, foram identificados erros e limitações. A primeira subseção documenta um erro pontual que foi corrigido; as subseções seguintes descrevem problemas ainda em aberto, que estão sendo investigados e representam trabalho futuro para estabilização do sistema.

\subsection{Erro: Redirecionamento para \texttt{localhost:3000} no Fluxo de Reset de Senha}

Ao solicitar a recuperação de senha pela tela de autenticação, o Supabase envia um e-mail com um link de redefinição. Durante os testes, ao clicar nesse link, o navegador era redirecionado para \texttt{http://localhost:3000} — um endereço inválido em dispositivos reais — em vez de abrir o aplicativo via \textit{deep link}.

    \centering
    \includegraphics[width=\linewidth]{Testes/ResetPasswordEmail}\\[4pt]
    {\footnotesize (a) E-mail de redefinição recebido}
  \end{minipage}\qquad
  \begin{minipage}{0.45\textwidth}
    \centering
    \includegraphics[width=\linewidth]{Testes/ResetPasswordErrorLocalhost3000}\\[4pt]
    {\footnotesize (b) Erro ao seguir o link — redireciona para \texttt{localhost:3000}}
  \end{minipage}
  \caption{Erro de redirecionamento no fluxo de reset de senha}
  \label{fig:reset-error}
\end{figure}

\textbf{Causa}: o Supabase utiliza por padrão o valor configurado em \textit{Site URL} no painel de autenticação como destino do link de redefinição. Durante o desenvolvimento, esse campo estava configurado como \texttt{http://localhost:3000}, que não corresponde ao esquema de URI do aplicativo mobile.

\textbf{Solução}: a URL de redirecionamento deve ser atualizada no painel do Supabase (\textit{Authentication → URL Configuration}) para o esquema de URI profundo do aplicativo (por exemplo, \texttt{salespro://reset-password}), e o app deve registrar um \textit{deep link handler} para esse esquema via \texttt{expo-linking}, capturando os parâmetros de token da URL e iniciando o fluxo de redefinição de senha.

\subsection{Problema em Aberto: Funcionamento Offline Incompleto}

O SalesPro foi projetado para operar sem conectividade, mas os testes revelaram que o suporte offline não está totalmente implementado. A estratégia atual funciona corretamente no cenário esperado — conexão estável durante a abertura do app, seguida de uso em campo sem rede — mas apresenta falhas quando o Supabase fica indisponível de forma inesperada durante o uso.

Os problemas observados incluem:

\begin{itemize}
  \item \textbf{Inicialização sem rede}: ao abrir o aplicativo sem nenhuma conexão prévia, algumas telas que dependem de dados não armazenados em cache falham com erros não tratados, em vez de exibir os dados locais disponíveis ou uma mensagem amigável de indisponibilidade;
  \item \textbf{Supabase fora do ar}: quando o serviço Supabase se torna indisponível durante uma sessão ativa, requisições feitas pela aplicação retornam erros que nem sempre são capturados e apresentados corretamente ao usuário, podendo resultar em telas vazias ou travamentos silenciosos;
  \item \textbf{Cobertura parcial do cache}: apenas as telas de recebimentos e clientes possuem cache local implementado via AsyncStorage. Módulos como produtos, relatórios e o dashboard não possuem fallback offline, tornando-os inacessíveis sem conexão.
\end{itemize}

\textbf{Status}: em investigação. A solução completa exige a extensão da camada de cache para todos os módulos, a padronização do tratamento de erros de rede em todos os serviços e a implementação de um estado global de conectividade que adapte o comportamento da UI antes de tentar qualquer requisição ao back-end.

\subsection{Problema em Aberto: Conflitos de Merge em Múltiplos Dispositivos}

O mecanismo de sincronização offline do SalesPro foi concebido para um cenário de uso individual em um único dispositivo. Quando a mesma conta é acessada em dois ou mais dispositivos e operações são realizadas offline em ambos, a sincronização posterior pode gerar inconsistências nos dados.

O problema ocorre porque a fila de sincronização (\texttt{SYNC\_QUEUE}) é local a cada dispositivo e não possui nenhum mecanismo de detecção de conflitos. Ao drenar a fila, as operações são enviadas ao Supabase na ordem em que foram registradas localmente, sem comparar o estado atual do banco com o estado que o dispositivo tinha quando a operação foi criada. Isso pode resultar em:

\begin{itemize}
  \item \textbf{Sobrescrita de dados}: um recebimento registrado no dispositivo A e sincronizado pode ser sobrescrito pela sincronização posterior do dispositivo B, que enfileirou uma operação sobre o mesmo registro;
  \item \textbf{Duplicações}: em cenários onde o mesmo recebimento é registrado manualmente nos dois dispositivos antes de qualquer sincronização, ambas as operações são enviadas ao banco sem detecção de duplicidade;
  \item \textbf{Estado inconsistente}: após conflitos não detectados, o estado exibido em cada dispositivo pode divergir do estado real no banco, sem notificação ao usuário.
\end{itemize}

\textbf{Status}: em aberto. A resolução requer a adoção de uma estratégia de resolução de conflitos — como \textit{last-write-wins} com \textit{timestamp} de criação da operação, ou versionamento de registros com \textit{vector clocks} — que ainda não foi implementada.

\subsection{Problema em Aberto: Instabilidade do Módulo de Sincronização}

Decorrente dos dois problemas anteriores, o módulo de sincronização (\texttt{sync.service.ts} e \texttt{SyncContext}) encontra-se em estado instável durante o desenvolvimento desta versão do projeto. As tentativas de ampliar a cobertura offline e de tratar os conflitos de múltiplos dispositivos introduziram regressões pontuais que ainda estão sendo corrigidas.

Os comportamentos instáveis observados incluem:

\begin{itemize}
  \item O auto-sync a cada 3 minutos, em algumas situações de erro de rede, entra em estado de \textit{retry} contínuo sem exibir corretamente o status de erro no menu lateral;
  \item A contagem de operações pendentes exibida no menu pode não refletir com precisão o tamanho real da fila após sincronizações parcialmente bem-sucedidas;
  \item Em dispositivos com versões mais antigas do AsyncStorage, a serialização da fila ocasionalmente falha de forma silenciosa, descartando operações pendentes.
\end{itemize}

\textbf{Status}: em correção ativa. O módulo de sincronização está sendo refatorado para separar com mais clareza as responsabilidades de enfileiramento, envio e tratamento de falhas, com o objetivo de estabilizar o comportamento antes de uma eventual versão de produção do aplicativo.

\subsection{Problema em Aberto: Controle de Estoque Não Implementado}

Durante os testes do fluxo de vendas, identificou-se que o aplicativo não realiza nenhuma verificação nem atualização do estoque dos produtos ao registrar uma venda. O campo \texttt{stock} existe na tabela \texttt{products} e é exibido na tela de gestão de produtos, mas não é consumido nem modificado pelo serviço de vendas.

Os comportamentos problemáticos observados incluem:

\begin{itemize}
  \item \textbf{Ausência de validação}: é possível registrar uma venda com quantidade superior ao estoque disponível sem que o sistema emita qualquer alerta ou bloqueio;
  \item \textbf{Estoque não decrementado}: após a confirmação de uma venda, o estoque dos produtos incluídos nos itens (\texttt{sale\_items}) não é subtraído — o valor de \texttt{stock} permanece inalterado no banco;
  \item \textbf{Inconsistência visual}: o vendedor visualiza um estoque na tela de produtos que não reflete o que foi efetivamente comprometido pelas vendas realizadas.
\end{itemize}

\textbf{Causa}: o serviço \texttt{salesService.create} realiza apenas a inserção do cabeçalho da venda, dos itens (\texttt{sale\_items}) e, quando parcelada, das parcelas (\texttt{sale\_installments}). Nenhuma etapa do fluxo executa o decremento de \texttt{stock} em \texttt{products} nem valida se a quantidade solicitada está disponível.

\textbf{Solução}: a correção envolve duas etapas no serviço \texttt{salesService.create}. Primeiro, antes de inserir a venda, verificar se o estoque de cada produto é suficiente para a quantidade pedida, abortando com mensagem de erro caso contrário. Segundo, após a inserção bem-sucedida dos itens, decrementar o campo \texttt{stock} de cada produto pela respectiva quantidade vendida, preferencialmente via uma chamada atômica ou dentro de uma transação para evitar inconsistências em caso de falha parcial.

\textbf{Status}: em aberto. A funcionalidade de controle de estoque não foi implementada nesta versão e constitui um dos principais pontos de evolução para versões futuras do aplicativo.

O SalesPro entrega uma solução completa e funcional para o autônomo de vendas porta a porta. A combinação de React Native com Expo garantiu uma base de código única para Android e iOS, enquanto o Supabase eliminou a necessidade de desenvolver infraestrutura de back-end própria, permitindo que o time concentrasse esforços na experiência do usuário e nas regras de negócio.

As principais entregas do projeto foram: autenticação segura com sessões persistidas e toggle show/hide de senha, cadastro completo de clientes com geocodificação automática via Nominatim, catálogo de produtos com arquivamento, fluxo de venda com carrinho e parcelamento automático, calendário de vencimentos com rastreamento visual de status, controle de recebimentos em modo manual e em modo de rota com interface de swipe, relatórios analíticos com filtros de período e otimização de rotas de cobrança com heurística do vizinho mais próximo partindo da localização GPS real do vendedor. O suporte offline foi parcialmente implementado via AsyncStorage e fila de sincronização, cobrindo o cenário principal de uso em campo, mas ainda apresenta limitações em situações de indisponibilidade inesperada do servidor e uso simultâneo em múltiplos dispositivos — pontos identificados nos testes e que constituem o principal trabalho em aberto para versões futuras do aplicativo.

A escolha por um algoritmo de otimização local em vez de APIs de roteamento externas reflete a realidade operacional dos usuários do sistema: vendedores em campo com conectividade instável que precisam de uma ferramenta confiável independentemente do sinal. O uso da posição GPS do dispositivo como ponto de partida da rota garante que a sequência calculada reflita a situação real do vendedor no momento da saída, evitando que a ordenação por urgência financeira sobreponha a eficiência geográfica. Essa decisão de arquitetura demonstra que é possível oferecer funcionalidade inteligente em aplicativos mobile sem sacrificar a robustez offline.

\section{Algoritmo de Haversine}

A função \texttt{haversineKm} em \texttt{screens/Recebimentos/helpers.ts} calcula a distância em quilômetros entre dois pontos geográficos:

\begin{verbatim}
function toRad(deg: number) { return (deg * Math.PI) / 180; }

function haversineKm(
  lat1: number, lon1: number,
  lat2: number, lon2: number
): number {
  const R    = 6371;
  const dLat = toRad(lat2 - lat1);
  const dLon = toRad(lon2 - lon1);
  const a =
    Math.sin(dLat / 2) ** 2 +
    Math.cos(toRad(lat1)) * Math.cos(toRad(lat2)) *
    Math.sin(dLon / 2) ** 2;
  return 2 * R * Math.asin(Math.sqrt(a));
}
\end{verbatim}

\section{Ordenação Geográfica na Rota de Recebimentos}

A função \texttt{nearestNeighborSort} reordena as paradas já selecionadas por urgência, partindo da localização GPS atual do vendedor para minimizar a distância total percorrida:

\begin{verbatim}
function nearestNeighborSort(
  stops: RouteStop[],
  originLat?: number,
  originLon?: number,
): RouteStop[] {
  if (stops.length < 2) return stops;

  const hasCoord = (s: RouteStop) =>
    s.sale.clients?.latitude != null &&
    s.sale.clients?.longitude != null;

  if (!stops.some(hasCoord)) return stops;

  const remaining = [...stops];
  const sorted: RouteStop[] = [];

  // Ponto inicial: cliente mais próximo da posição GPS atual,
  // ou a parada de maior urgência como fallback sem permissão GPS.
  if (originLat != null && originLon != null) {
    let nearestIdx  = 0;
    let nearestDist = Infinity;
    remaining.forEach((stop, i) => {
      const lat = stop.sale.clients?.latitude;
      const lon = stop.sale.clients?.longitude;
      if (lat == null || lon == null) return;
      const d = haversineKm(originLat, originLon, lat, lon);
      if (d < nearestDist) { nearestDist = d; nearestIdx = i; }
    });
    sorted.push(remaining.splice(nearestIdx, 1)[0]);
  } else {
    sorted.push(remaining.splice(0, 1)[0]);
  }

  while (remaining.length > 0) {
    const last    = sorted[sorted.length - 1];
    const lastLat = last.sale.clients?.latitude;
    const lastLon = last.sale.clients?.longitude;

    if (lastLat == null || lastLon == null) {
      sorted.push(remaining.splice(0, 1)[0]);
      continue;
    }

    let nearestIdx  = 0;
    let nearestDist = Infinity;

    remaining.forEach((stop, i) => {
      const lat = stop.sale.clients?.latitude;
      const lon = stop.sale.clients?.longitude;
      if (lat == null || lon == null) return;
      const d = haversineKm(lastLat, lastLon, lat, lon);
      if (d < nearestDist) { nearestDist = d; nearestIdx = i; }
    });

    sorted.push(remaining.splice(nearestIdx, 1)[0]);
  }

  return sorted;
}
\end{verbatim}

A função \texttt{buildRoute} seleciona as paradas por urgência (Equação~\ref{eq:maxstops}), recebe a localização GPS do chamador e delega a reordenação geográfica à \texttt{nearestNeighborSort}:

\begin{verbatim}
export function buildRoute(
  sales: PendingSale[],
  workHours: number,
  avgMins: number,
  targetDate: Date,
  originLat?: number,
  originLon?: number,
): { route: RouteStop[]; excluded: RouteStop[] } {
  const maxStops = Math.max(1,
    Math.floor((workHours * 60) / avgMins));

  const scored = sales.map(sale => {
    const due    = effectiveDueDate(sale);
    const days   = getDays(due, targetDate);
    const status = getStatus(due, targetDate);
    const city   = sale.clients?.municipio?.nome ||
      sale.clients?.address?.split(',')[0]?.trim() || 'Sem cidade';
    return { sale, status, days, total: pendingTotal(sale), city };
  });

  const priorityOf = (s: RouteStop) => {
    if (s.status === 'overdue') return -1000 + s.days;
    if (s.status === 'today')   return 0;
    if (s.status === 'week')    return s.days;
    return 100 + s.days;
  };

  const pool     = [...scored].sort(
    (a, b) => priorityOf(a) - priorityOf(b));
  const selected = pool.splice(0, maxStops);
  const route    = nearestNeighborSort(selected, originLat, originLon);

  return { route, excluded: pool };
}
\end{verbatim}
